🎯 Résumé exécutif

L'analyse de l'ensemble des modules Veraluz OS révèle une base solide sur les modules core (Auth, Réservations, Paiements, Restaurant) avec des lacunes critiques sur les modules récents (Housekeeping, Notifications, Finance). L'architecture multi-tenant est correctement posée autour de la colonne property_id, mais l'intégration globale ne peut pas se faire en l'état — 11 problèmes bloquants doivent être résolus en priorité.

🔴 3 Blockers critiques (à corriger AVANT intégration)
  • Modules Housekeeping et Notifications ont une DB + maquette mais zéro API route dans Next.js — inutilisables en production
  • Finance référence auth.users(id) au lieu de app_users(id) — bypass du modèle utilisateur, casse les jointures RH/profiles
  • Middleware Next.js ne protège pas /hr, /analytics, /housekeeping, /notifications — routes accessibles non authentifiées
⚠️ 8 Problèmes majeurs (à corriger avant déploiement prod)
  • Incohérence de préfixe SQL — migrations 007-010 omettent public. (risque si search_path change)
  • TAB_ACCESS manque 4 entrées : hr, housekeeping, notifications, analytics
  • PERMISSIONS manque 9 actions pour les nouveaux modules
  • Sidebar ne contient pas les liens HR, Housekeeping, Notifications, Analytics
  • Pattern d'auth dupliqué dans 15+ routes API — aucun middleware centralisé
  • types/index.ts ne couvre pas 4 modules (HK, Notifications, Finance, HR complet) — TypeScript partiel
  • Tables analytics sans préfixe de schéma cohérent (analytics_*) vs rest (public.table_name)
  • Page /invoices dans la sidebar mais aucun fichier app/(dashboard)/invoices/page.tsx
✅ Ce qui fonctionne bien
  • Architecture multi-tenant correcte — property_id présent sur toutes les tables core
  • RLS activé sur toutes les tables (100% couverture dans les migrations)
  • Pattern createClient() de lib/supabase/server.ts adopté par 14/15 routes
  • lib/auth/permissions.ts bien structuré — requirePermission, requireTabAccess, logAuthEvent
  • lib/utils/index.ts : utilitaires FCFA, dates, CN, overlap — réutilisables partout
  • Triggers PostgreSQL bien utilisés : checkout → tâche HK automatique
  • Workflow d'approbation dépenses 4 niveaux (ENUM + FK) correctement modélisé
  • Realtime Supabase activé sur notifications et system_events

Verdict architecture

La colonne vertébrale est bonne. Le problème est que les 4 derniers modules ont été conçus Database-first (migrations SQL ✅) et UI-first (maquettes HTML ✅) mais sans la couche intermédiaire — les API routes et les composants React — qui permettrait de les connecter. C'est le chantier prioritaire.

2️⃣ Cohérence des API routes

Pattern d'authentification — 2 patterns coexistent

🔴 Pattern A — Obsolète (reservations/create uniquement)

// ❌ Import inline de createServerClient au lieu de lib/supabase/server
import { createServerClient } from '@supabase/ssr'
// + logAuthEvent importé — mais pas utilisé dans les autres routes

✅ Pattern B — Standard (14/15 routes)

import { createClient } from '@/lib/supabase/server'
const supabase = await createClient()
const { data: { user } } = await supabase.auth.getUser()
if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

Duplication critique — vérification de rôle inline (15 routes)

Chaque route répète manuellement la même logique de vérification d'accès. En l'absence d'un helper centralisé, un oubli dans une seule route crée une faille de sécurité non détectable.

// ❌ Pattern répété dans CHAQUE route (15+ fois) :
const { data: up } = await supabase.from('user_properties').select('role')
  .eq('user_id', user.id).eq('property_id', property_id).single()
if (!up || !ALLOWED_ROLES.includes(up.role))
  return NextResponse.json({ error: '...' }, { status: 403 })

// ✅ Ce qui devrait exister dans lib/api/withAuth.ts :
export async function withAuth(req, propertyId, allowedRoles, handler) {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return json({ error: 'Unauthorized' }, 401)
  const { data: up } = await supabase.from('user_properties')
    .select('role').eq('user_id', user.id).eq('property_id', propertyId).single()
  if (!up || !allowedRoles.includes(up.role)) return json({ error: 'Forbidden' }, 403)
  return handler(req, { user, role: up.role, supabase })
}

Bug détecté — HR employees route

// ❌ lib/api/hr/employees/route.ts — import incorrect ligne 51

// Le module permissions.ts exporte getAdminClient, PAS createClient

8️⃣ Dépendances dangereuses

Finance → auth.users (bypass app_users)
Chemin : expense_requests.submitted_by → auth.users(id)
Danger : Aucun accès aux champs du profil utilisateur (name, phone, department). Jointures Finance + RH impossibles proprement. Si on supprime un utilisateur de app_users mais pas de auth.users, les données Finance pointent vers un "fantôme".
🔴 Bloquant production
Trigger HK → reservations (couplage fort)
Chemin : fn_auto_create_hk_task() lit reservations.unit_id, reservations.client_id, reservations.total
Danger : Toute modification du schéma reservations (renommage colonne, suppression) casse silencieusement le trigger. Pas de test unitaire possible sans les deux tables.
⚠️ Risque moyen — documenter dans migration
Analytics → 3 tables (snapshot fragile)
Chemin : analytics_daily_snapshots agrège reservations, payments, restaurant_orders
Danger : Si le calcul du snapshot est un trigger/cron et que l'une des 3 tables change de schéma, les snapshots deviennent silencieusement incorrects (pas d'erreur, données fausses).
⚠️ Risque moyen — ajouter des assertions
HR employees → import dynamique incorrect
Chemin : app/api/hr/employees/route.ts ligne 51 : import('@/lib/auth/permissions').createClient
Danger : permissions.ts n'exporte pas createClient — cet import échoue à runtime. Le code passe en compilation TypeScript mais crash en production.
🔴 Bug runtime
Notifications sans lien FK vers system_events
Chemin : Table notifications n'a pas de FK vers system_events
Danger : Une notification peut référencer un event_id inexistant. Les events peuvent être supprimés sans cascader sur les notifications liées.
ℹ️ Risque faible — intégrité référentielle

Convention API — pattern unifié

// ✅ lib/api/withAuth.ts — à créer
import { createClient } from '@/lib/supabase/server'
import { NextRequest, NextResponse } from 'next/server'
import type { OrgRole } from '@/types'

type AuthContext = { user: User; role: OrgRole; supabase: SupabaseClient; propertyId: string }
type Handler = (req: NextRequest, ctx: AuthContext) => Promise<NextResponse>

export function withAuth(allowedRoles: OrgRole[], handler: Handler) {
  return async (req: NextRequest) => {
    const supabase = await createClient()
    const { data: { user } } = await supabase.auth.getUser()
    if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

    const propertyId = req.nextUrl.searchParams.get('property_id')
      ?? (await req.clone().json().catch(() => ({}))).property_id
    if (!propertyId) return NextResponse.json({ error: 'property_id requis' }, { status: 400 })

    const { data: up } = await supabase.from('user_properties')
      .select('role').eq('user_id', user.id).eq('property_id', propertyId).single()
    if (!up || !allowedRoles.includes(up.role as OrgRole))
      return NextResponse.json({ error: 'Permission refusée' }, { status: 403 })

    return handler(req, { user, role: up.role as OrgRole, supabase, propertyId })
  }
}

// ✅ Usage dans n'importe quelle route :
export const GET = withAuth(['owner', 'hotel_manager', 'housekeeping'], async (req, { supabase, propertyId }) => {
  const { data } = await supabase.from('housekeeping_tasks').select('*').eq('property_id', propertyId)
  return NextResponse.json({ data })
})
