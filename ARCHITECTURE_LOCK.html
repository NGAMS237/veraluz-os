🔗 Analyse des dépendances
✅
Couplage fort : 0 cas détecté Aucun module n'importe, n'appelle, ni ne lit des symboles internes d'un autre module.
⚠️
Dépendance implicite : CSS variables partagées non centralisées 20 variables CSS (--accent, --bg, --border, --green, etc.) sont redéfinies dans chaque module. Si un module change sa palette, les autres restent incohérents visuellement. Solution : créer un fichier shared/veraluz-theme.css chargé par tous.

Le bridge inclut un fallback console.log, mais aucun affichage visuel. Solution : ajouter un toast de fallback local minimal dans le bridge.
ℹ️
Dépendance acceptable : Event Bus Core Les modules émettent des événements vers le Core via emitToCore(). C'est la communication autorisée. Cette dépendance est unidirectionnelle et contrôlée — elle ne crée pas de couplage fort.

Règles Architecture Veraluz OS — Verrouillées v1.0

Ces règles s'appliquent à toute future modification du code. Aucune exception sans validation explicite.

📜 Règle 1 — Isolation absolue des modules
🚫 INTERDIT : Accès direct au code d'un autre module
Un module ne peut JAMAIS appeler des fonctions, lire des variables, ou modifier le DOM d'un autre module, directement ou via window.frames, window.parent.modules, ou tout autre mécanisme.

Seuls canaux autorisés :
  • emitToCore(type, data) — module → Core
  • window.addEventListener('message', ...) — écoute broadcast du Core
  • API REST partagées (quand backend connecté)
✅ AUTORISÉ : Communication via Event Bus
Tous les événements inter-modules passent par le Core. Le Core est le seul broker d'événements autorisé.
📜 Règle 2 — Le Core est un orchestrateur, pas un module
🚫 INTERDIT : Logique métier dans le Core
Le Core ne doit pas contenir : calculs de prix, gestion d'inventaire, logique de réservation, traitement de paiements, gestion RH.

Ce que le Core peut contenir :
  • Configuration des modules (labels, icônes, permissions)
  • Données de démo globales (DEMO_DATA) — seulement pour le dashboard
  • Gestion des sessions et des rôles utilisateurs
  • Navigation et routing entre modules
  • Event Bus et dispatch d'événements
  • Notifications système (non métier)

  • ❌ Variables globales nommées sans le préfixe du module
📜 Règle 5 — Périmètre de modification IA
⚠️ Règle d'isolation pour Claude/IA
Lorsqu'une modification est demandée sur un module spécifique, Claude doit :
  1. Lire uniquement le fichier du module concerné (MODULE_EMBEDDED.html)
  2. Modifier uniquement ce fichier — aucun autre module ne doit être touché
  3. Ne pas modifier VERALUZ_OS_CORE.html sauf si la demande concerne explicitement le Core
  4. Vérifier que les modifications ne cassent pas l'interface embedded (pas de sidebar/topbar ajoutée)
  5. Tester la syntaxe JS avec node --check avant livraison
  6. Documenter les événements nouveaux dans la liste des types d'événements
